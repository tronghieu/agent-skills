# Product Manager

**语言：** [中文](./README.zh.md) | [English](./README.md) | [Tiếng Việt](./README.vi.md)

将产品证据转化为可辩护的决策、可执行的产物，以及团队可以持续回看的记录。

## 安装

```bash
npx skills add tronghieu/agent-skills --skill product-manager
```

## 立即尝试

```text
/product-manager 为这些机会排序，并说明哪些排名会随假设变化而改变。
/product-manager 根据这些反馈为离线模式写一份 PRD，并明确本次发布的范围边界。
/product-manager 为这次计费变更设计发布计划，包括预先承诺的回滚标准。
/product-manager 将这些支持工单转化为产品机会，并说明它们挑战了哪项决策。
```

## 为什么不只用普通聊天机器人？

普通聊天机器人能用听起来合理的猜测，生成漂亮的 RICE 表或 PRD。这个副驾驶会让不确定性保持可见：每个决策数字都关联来源、带范围的假设，或你提供的带日期估计；依赖假设的结论会做敏感性分析；缺乏证据的工作会明确标为一次押注。PRD、优先级和发布计划会在你据此行动前接受可见的对抗性检查。

## 适合谁

适合负责产品决策、并与用户、工程、设计、支持、销售和业务利益相关者协作的产品经理、产品负责人和创始人。最终决策仍由你负责；副驾驶负责界定选择、指出与现有证据相矛盾之处，并保存决策轨迹。

典型场景包括：

- 将原始反馈转为与证据相连的机会，而不是功能请求清单。
- 用 RICE 和敏感性分析排列独立机会；用 Kano 检验期望类型，而不是伪造排名。
- 用 job story、story map、可测试的验收标准和明确的 Won't-have 边界，在 PRD 中定义已选问题。
- 定义北极星指标、指标树、护栏指标和以结果为导向的 OKR。
- 设计在结果出现前就确定通过、失败和下一步行动的实验。
- 规划按风险分级的 rollout、量化 stage gate、回滚标准和发布后复盘。
- 决定平台还是功能，或做轻量、证据驱动的定价与包装选择。

## PM 纪律

这是一本 playbook，而不是固定阶段的流程：从你当下需要的决策切入。对于持续性工作，它会先回到当前状态和既有决策；对于一次性请求，它会交付所需产物，而不强迫你建立一套仪式。

循环是：收集证据和反馈 → 界定用户任务与机会 → 排序 → 规格化和划定范围 → 度量 → 测试风险最高的信念 → 安全发布 → 将学习反馈到下一个决策。产品工作区会跨会话保存证据登记、假设、机会、指标、产物、决策日志和当前状态。每个决策都会记录理由、必要时的异议，以及重新审视的触发条件。

每种框架各司其职：job story 界定问题；RICE 比较机会；story mapping 分解已选机会；MoSCoW 划定发布线；Kano 检验期望类型。缺失输入会被询问，或登记为带范围的诚实假设，绝不悄悄补全。

## 需要提供什么，会得到什么

带来你已有的任何材料：产品背景、目标用户、反馈、研究、分析数据、业务约束、工程估算以及待解决的决策。数据不必完整。副驾驶会区分证据与假设，并说明哪些信息会改变建议。

根据所用 play，你会得到与证据关联的机会 backlog；带敏感性说明的优先级；PRD 和 story map；带标注 baseline 的指标定义或 OKR；在实验前冻结的 experiment card；含回滚条件的 launch plan；或已记录的平台、功能或定价决策。回复会直接给出建议和限制，而不是把结论藏在工作区里。

## 互补技能

以下技能为可选项，不是前提：

- [design-thinking](../design-thinking/README.zh.md) — 当你需要深度用户发现时使用：访谈、田野研究、原型测试，或理解用户为何、如何体验问题。其证据可以为这个产品工作区提供输入。
- [market-researcher](../market-researcher/README.zh.md) — 当需要外部市场事实时使用：竞争背景、市场规模、定价基准，或超过少量快速核查的、有来源的支付意愿证据。
- [strategy-board](../strategy-board/README.zh.md) — 当决策高于产品层级时使用，例如进入新市场、build-versus-buy，或停止一条产品线。

## 限制

该技能不会编造用户研究、市场事实、分析数据、工程估算、实验结果或客户引语。它设计实验，但不模拟结果；一手发现应使用 design-thinking，更广泛的公司战略应使用 strategy-board。它支持产品决策和交接，不负责实现产品。
