# Manual Testing

**Language:** [English](./README.md) | [Tiếng Việt](./README.vi.md) | [中文](./README.zh.md)

像一个多疑的测试员那样手动测试运行中的应用，并在称之为 bug 之前用数据库证明每一个发现。

```bash
npx skills add tronghieu/agent-skills --skill manual-testing
```

## 快速开始

```text
对邀请流程做一次探索性测试。限时 30 分钟。
```

```text
验证 bug #214 的修复：订单总额忽略了折扣。
```

```text
部署后冒烟测试：登录、新建一条记录、检查列表。
```

```text
审查结账页面的越南语文案。
```

```text
向应用内助手提五个关于该租户订单的问题，并把回答对照数据库核实。
```

## 为什么不直接点一点？

驱动浏览器的 agent 只能看到页面显示的内容。页面会撒谎：提示"已保存"但数据行从未落库，列表为空只是因为筛选条件错了，错误在到达屏幕前就被吞掉。只靠截图写出的报告会产生假 bug，而一个假 bug 损失的信任比十个真 bug 赢得的还多。

这个 skill 把 UI 当作三个证人之一。每个发现都经过三方核对：屏幕显示了什么，数据行说了什么，网络和控制台记录了什么。"我无法测试"是 UNVERIFIED，永远不是 FAIL。像文案难懂这类主观判断保留为 OBSERVATION 交给人决定，不附带结论。

## 适合谁

自动化测试只复查已知承诺的团队，需要有人去找剩下的部分：没人预料到的 bug、修复后把旁边功能弄坏、某个语言下读起来不对的页面、自信却答错的 AI 助手。

## 工作方式

1. **加载项目的测试策略。** `scripts/resolve_customization.py` 把 skill 默认值与团队覆盖 `_project/testing/manual-testing.toml` 及个人 `.user.toml` 合并。其中指定的策略文档在整个会话中保持在上下文里，并优先于 skill 自身默认值。
2. **读取项目适配器。** 端口、服务、种子账号、认证方式、输出路径和预检步骤来自 `_project/testing/environment.toml`。带日期的"当前状态"快照和操作指南来自 `environment.md`。只读 SQL 来自 `verification-queries.md`。在新仓库中，skill 从模板生成适配器，每个值都从真实文件读取，标记无法确认的项，并在第一次会话前先询问。
3. **选择模式并写下任务。** 探索（一个 charter）、验证（一个可证伪的断言）、冒烟（固定的广度清单）、评估（一个视角覆盖一组页面）或 AI 探测（有依据的问题集）。拿到测试设计或用例编号时，先区分哪些条件真正需要人来做。
4. **操作并记录。** 浏览器自动化加持续日志：动作、观察、结论。每一步之后检查：控制台、网络、i18n key、租户泄漏、权限边界、静默失败。
5. **先核实再下结论。** 对本地数据库执行只读 SELECT。任何 FAIL 之前先自检：账号正确、元素正确、页面已加载、从干净状态能复现两次。
6. **报告。** 一份带覆盖图的会话记录，每个 FAIL 一份 bug 报告，以及以"场景加判定依据"形式写出的自动化候选项。

## 你会得到什么

- 一份会话记录，即使什么都没发现，也写明去过哪里、跳过哪里、没到哪里。
- 每个失败一份 bug 报告，足够让不在场的开发者复现。
- 需要人判断的观察项，与结论分开保存。
- 自动化候选项：下一步该交给 e2e 或集成测试的内容。

## 限制

skill 只在本地开发环境运行。它从不写数据库，任何不可逆操作前都会先问。数据库核实假定有一个可通过 `psql` 或等价只读客户端访问的 SQL 数据库。它不写自动化测试，只指出该自动化什么。发现的可信度受适配器限制：过期的 `environment.md` 会对一个已不存在的应用版本给出自信的发现，所以适配器带日期并就地重写，不追加。
