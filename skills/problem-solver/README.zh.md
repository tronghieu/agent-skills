# Problem Solver

**语言：** [中文](./README.zh.md) | [English](./README.md) | [Tiếng Việt](./README.vi.md)

将原因未知的运营、技术、流程或业务故障，转化为可验证的诊断和针对根因的行动计划。

## 安装

```bash
npx skills add tronghieu/agent-skills --skill problem-solver
```

## 用真实问题开始

```text
/problem-solver 订单从六月起开始延迟交付；只有跨区的定制订单受影响。我们应先检查什么？
```

```text
/problem-solver 本月转化率下降了 18%。我们改了定价、引导流程和广告定向；请帮我们区分这些原因。
```

```text
/problem-solver 每次热修复后生产事故都会复发。请先做根因诊断，再提出下一步修复方案。
```

## 为什么不直接让普通聊天机器人给修复方案？

普通聊天可能会用缺失的事实编出一个听起来合理而自信的故事。Problem Solver 会把你已观察到的内容与尚属猜测的内容分开，要求用成本最低、能够推翻主要解释的检查来验证，而且不会把一个看似诱人的修复当成原因的证据。因此，失败的测试也是有价值的进展，而不是被漂亮回答掩盖的麻烦。

## 适用时机

当某件事正在故障、变慢、反复发生或出现变化，而原因未知或未经验证时使用：交付延迟模式、指标下滑、反复事故、停滞的变更，或需要落实行动的复盘。它适合能提供观察结果或检查真实世界的运营负责人、工程师、产品/流程负责人、经理和企业主。

如果没有任何故障、你只需要开放式创意，或问题本质是理解用户需求与行为，它并非首选。

如果你在原因未知时直接索要修复方案，它会说明这些想法可能瞄错目标，提供一次快速“界定”，并让你在理解风险后明确跳过诊断；一旦跳过，工作会转交给 Brainstorm Coach。

## 心智模型：先诊断，后解决

该技能依赖三种真相来源：

- 你直接知道、或由你检查过的数据和材料支持的**事实**标为 `[verified]`。
- **假设**，包括你的直觉和引导者的候选解释，在现实确认前都标为 `[assumed]`。
- **验证**只有在你检查真实世界时才发生；“听起来合理”并不算验证。

影响结论的假设会记录置信度、出错影响及成本最低的检查。每个根因候选都必须预测“若为真应看到什么”，并说明能推翻它的最便宜观察。至少保留两个竞争解释，直到证据把它们区分开。

## 一次会话如何进行

1. **界定** — 澄清可观察症状、开始时间、影响、已尝试的修复和“修好”的判据；把事实与夹带的原因、偏好方案分开。
2. **划界** — 比较问题在何处、何时、影响谁/什么、以何种形式**存在**与**不存在**。差异提供最强线索。
3. **诊断** — 按问题形态使用一到两种方法：可能是线性链条时用 Five Whys，多因素时用鱼骨图，反复或越修越糟的模式用因果回路；组织变更可附加力场/约束分析。
4. **解决** — 围绕已验证原因生成选项，并把每个选项追溯到它处理的原因。必要的症状补丁会被标注，并配套因果修复。
5. **决策** — 两个选项直接比较；三个及以上才使用矩阵。每个评分都要引用证据，或写明 `unknown — assumption`。决定由你作出。
6. **计划** — 选择试点、分阶段实施，或少见的可逆式一次性上线；明确负责人、继承而来的成功指标、未结假设检查、复盘点和转向触发条件。

流程随风险而伸缩：小问题可以合并前几个阶段，昂贵或反复的问题才值得完整管线。若你的开场已包含清晰边界和同时发生的变更，技能可以在第一轮提出一个廉价的区分性检查，而不是让你先填写问卷。

## 关口、角色与协作

只有三个关口：你确认精炼后的问题陈述；主要原因候选得到验证——或者你明确承担继续推进的风险；以及你作出最终决定。该技能不会角色扮演利益相关者，也不会编造他们会说什么。视角问题只能帮助扩展鱼骨图，而你始终是事实来源。

在“解决”阶段，如可用，它会交接给 [Brainstorm Coach](../brainstorm-coach/README.zh.md) 做围绕原因的发散创意；若不可用，则继续轻量、以用户想法优先的创意过程，不会因缺少配套技能而停下。它不定义常驻多智能体小组或“party”。

## 体验与交付物

请带来你知道的内容：可观察症状和量级、时间、受影响与未受影响的情况、近期变更、已尝试的做法、数据/材料、约束和成功定义。“目前不知道”是有效答案，会成为需要检查的事实缺口。

对于跨越多次对话的问题，技能通常维护一个精简工作区：问题陈述与边界、诊断与测试、假设日志、可追溯原因的选项、决策和计划。你回来后，它会先读取这些状态，概括待完成的检查，根据新证据更新标签和置信度，并从当前阶段继续，不会从头开始。对于小问题，同样的结构可以直接保留在对话中。

你将得到：确认的问题陈述；Is/Is-Not 边界；带标签、含竞争候选与验证测试的原因树；假设日志；可追溯到原因的选项；考虑证据的建议；以及含指标和转向触发条件的实施计划。

## 配套技能

- [Brainstorm Coach](../brainstorm-coach/README.zh.md) — 根因验证后，用于扩展解决方案。
- [Design Thinking](../design-thinking/README.zh.md) — 当真正的不确定性在于用户需求、感受、采用或行为时。
- [Critical Thinking](../critical-thinking/README.zh.md) — 用于审查诊断或决策的推理。
- [Strategy Board](../strategy-board/README.zh.md) — 当选定修复已成为公司级战略押注时。
- [Market Researcher](../market-researcher/README.zh.md) — 当原因或方案依赖你尚未掌握的市场事实时。
- [Project Manager](../project-manager/README.zh.md) — 当计划变成包含多个工作流和利益相关者的多周项目时。

## 限制

Problem Solver 无法自行查看你的系统，也无法验证你尚未提供或检查过的事实。它不会捏造整齐的因果链，不保证干预一定成功，也不能取代领域、安全、法律或运营判断。你可以在验证完成前行动，但相关分支会明确标为有风险，计划应采用可逆试点和转向触发条件。
